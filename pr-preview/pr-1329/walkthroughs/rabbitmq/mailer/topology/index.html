The topology

The mailer’s exchanges, queues, bindings and policies in a RabbitMQ definitions file, importing it into the broker, and creating the logins and their permissions with rabbitmqctl.

The mailer declares nothing. Its topology is deploy/rabbitmq/definitions.json, a definitions file the broker’s team imports. It holds no users and no passwords.

Four exchanges, each durable:

"exchanges": [
  {
    "name": "mail",
    "vhost": "/",
    "type": "direct",
    "durable": true,
    "auto_delete": false,
    "internal": false,
    "arguments": {}
  },
  {
    "name": "mail.retry",
    "vhost": "/",
    "type": "direct",
    "durable": true,

    "internal": false,
    "arguments": {}

    "name": "mail.dead",

The policies

The delays and limits are policies, since RabbitMQ changes a policy in place but a queue’s arguments only by deleting the queue:

"policies": [
  {
    "name": "mail.send",
    "vhost": "/",
    "pattern": "^mail\\.send$",
    "apply-to": "queues",
    "priority": 0,
    "definition": {
      "delivery-limit": 5,
      "dead-letter-exchange": "mail.dead",
      "dead-letter-strategy": "at-least-once",
      "overflow": "reject-publish"
    }
  },
  {
    "name": "mail.send.retry",
    "vhost": "/",
    "pattern": "^mail\\.send\\.retry$",
    "apply-to": "queues",
    "priority": 0,
    "definition": {
      "message-ttl": 300000,
      "dead-letter-exchange": "mail",
      "dead-letter-routing-key": "mail.send",
      "dead-letter-strategy": "at-least-once",
      "overflow": "reject-publish"
    }
  }
]
  • mail.send dead-letters a message to mail.dead after 5 deliveries.
  • mail.send.retry holds a parked request for 5 minutes, then dead-letters it back to mail by mail.send.
  • At-least-once dead-lettering needs overflow reject-publish.

Retries and dead letters shows how the mailer uses them.

Importing it

Into a running broker:

rabbitmqctl import_definitions definitions.json

The kind overlay imports a second file after it, with policies of a higher priority, so a test waits 1s for a parked request and 2 deliveries for the delivery limit:

{
  "name": "kind.mail.send",
  "vhost": "/",
  "pattern": "^mail\\.send$",
  "apply-to": "queues",
  "priority": 1,
  "definition": {
    "delivery-limit": 2,
    "dead-letter-exchange": "mail.dead",
    "dead-letter-strategy": "at-least-once",
    "overflow": "reject-publish"
  }
},
{
  "name": "kind.mail.send.retry",
  "vhost": "/",
  "pattern": "^mail\\.send\\.retry$",
  "apply-to": "queues",
  "priority": 1,
  "definition": {
    "message-ttl": 1000,
    "dead-letter-exchange": "mail",
    "dead-letter-routing-key": "mail.send",
    "dead-letter-strategy": "at-least-once",
    "overflow": "reject-publish"
  }
}

The logins

Create each login with a password read from a file, then grant it its configure, write and read permissions, in that order:

rabbitmqctl add_user mailer <mailer-password
rabbitmqctl set_permissions --vhost / mailer '^$' '^mail\.(retry|dead|events)$' '^mail\.send$'
PermissionThe mailer’sBecause
configurenoneit declares nothing
writemail.retry, mail.dead and mail.eventsit parks, dead-letters and publishes events
readmail.sendit consumes its work queue only

A service that asks for emails needs to write mail and nothing else, as the kind overlay’s mailrequest login does:

rabbitmqctl add_user mailrequest <mailrequest-password
rabbitmqctl set_permissions --vhost / mailrequest '^$' '^mail$' '^$'
